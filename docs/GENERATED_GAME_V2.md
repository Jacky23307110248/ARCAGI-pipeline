# Playable generated-game production

For phase-aware review, named independent probes, configuration contrasts and
closed evidence expressions, see [Validation programs](VALIDATION_PROGRAM.md).
The opt-in checking frontier and execution limits are explicit in that contract.

## Design and execution phases

Design review checks source-backed original functions, proposed observable
quantities and coherent validation plans. Concrete Python binding paths and
executed receipts can remain pending implementation. Required functions stay
explicit while bindings are repaired. Planned aliases are not runtime evidence.

Native GeneratedLevel.observation_bindings maps aliases to read-only paths from
the original engine instance. Machine observations expose values under projected.
Mappings follow the actual engine level position after automatic transitions.
Trace rows record engine_position; another target's projections cannot witness
the previous target's behavior. Missing adequate observations remain unknown.
Source-protocol engines own their original observe implementation and do not
accept this native binding option.

Completed replacement artifacts with self-addressed revision requests proceed
to downstream checks. Cross-stage requests keep their route and use the distinct
model_revision_requested diagnostic code. See [the release check](RELEASE_VALIDATION.md) for public regression evidence.

The default machine and production CLI target is `generated-game/v2`.
Workflow implementation tasks use that execution contract and supply pinned
production_api, design_validation_api, runtime_api and generated_game_api files.
The machine configuration names the same production_contract. The v1 library
and CLI remain available through explicit `design-production/v1` selection.

## Inputs and plugin interface

Frozen evidence, rules and blueprint retain their existing graph interfaces.
Blueprint adds production_target `{contract: "generated-game/v2", object:
"playable_generated_unit"}`. Each slot describes game_function, original
evidence, behavior_requirements and separate teaching_hypotheses.

The plugin factory accepts runtime context. Its generate_units method returns
GeneratedUnit objects with GeneratedLevel entries. Each entry has a blueprint
slot, playable configuration, goal, construction claims and optional initial
state declarations and novelty probe actions. Counts, mechanisms and ordering
come from these inputs. Model search pins the full configuration and goal hashes
and a model version in ModelSearch.evidence. Bounded results remain unknown.

For raw-arcengine, configuration.engine_level is a canonical native Level
snapshot; configuration may also contain the independent model's data.
compile_levels returns original native Levels matching those snapshots.
The core installs both live and clean Levels, resets, selects and plays through
the original engine implementation. Native goals express completed counts.
Other runtimes can implement the source-protocol driver methods in their original
hash-bound source; this profile's trust includes those original methods.

## Evidence and completion

Reports bind input fingerprints, generated artifact, model configuration, native
loaded configuration, source, environment, instance identity, target and actions.
Independent per-level replay and full-unit execution use separate instances.
Continuous execution never silently selects a successor level. Explicit
reset_each policy records the resets; full completion still requires the source
engine's complete result. Initial goals can use empty candidate paths when the
native goal and full-unit completion are actually satisfied.

Behavior predicates read machine-observed values. Unsupported claims retain
unknown. Structure, behavior and hypotheses have distinct proof scope. The
native driver observes frames and standard engine state; richer mechanisms
require a suitable observation protocol or separately evidenced experiment.
Selecting weak requirements cannot establish stronger semantic claims.
Original and peer-content comparisons require distinguishing runtime evidence;
when initial content is insufficient, supply comparable probes. Shared solution
paths alone do not imply duplicate configurations.

`generated_unit_verified/v2` requires accepted generated-level goals, required
behavior checks, full-unit execution and separate interface smoke. Unmet checks
produce archived structured feedback for the normal DS revision loop. Search
candidate labels remain model results; verified_solution records engine acceptance.

This ordinary local-process interface does not provide adversarial code isolation
or an automatic proof of model semantics, exhaustive-search correctness or
teaching benefit. Those responsibilities remain explicit in model self-review
and the source trust boundary.

## LS20 reference replay

Run from the repository with its declared LS20 environment and import roots:

```powershell
python -m examples.ls20.generated_v2 --output outputs/my-v2-replay --packages outputs/ls20/seed22/packages
```

Use a new output directory. The thin case adapter reuses frozen independent BFS
and native Level conversion. The three supplied seven-level packages are searched
and replayed individually and continuously. Their v2 behavior commitment is native
progress; historical detailed mechanism and necessity audits retain their own
reports and scope. The v2 regression establishes configuration/execution binding
and campaign completion, rather than re-proving every historical causal claim.
